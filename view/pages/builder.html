Live form

One tag per kind of control renders whatever matchSpec decided, every time. They never change between runs:

<b-field each="fields"></b-field>
<b-memo each="messages" rows="6"></b-memo>
<b-choice each="choices"></b-choice>
<b-check each="checks"></b-check>

Ask for a box to tick and you get one, and this is the newest thing on the page. Until 2026-08-14 the vocabulary had no verb that could operate a tick box: the only verb for a form control writes the control's value, and a tick box's value is what the form submits rather than whether it is ticked, so the write landed, reported success and moved nothing. Generating one before that would have put a control here the desk could not touch. A tick box carries a different kind of address from every other control on this page for exactly that reason, and the desk ticks it with a different verb.

Fields are grouped by kind, text fields first, then a message box, then choices, then anything to tick. Interleaving them in the order you asked isn't supported, on purpose, a v1 limit. Labels above are the closed set's own defaults; a model could reword them (matchSpec's applyWording seam exists for exactly that), but it isn't wired into this live page, because the in-browser model runs after the page has already rendered.

So be clear about who wrote what here: nothing on this page was written by the model. The labels are the closed set's, and the demo values the desk types in are drafted by code as well, because an action the desk performs never gets a model tail. What you are watching is selection and operation, which is the part a small model cannot do, and the wording pass is still an open seam rather than a shipped one.

The address each field carries sits on the control itself, so the desk writes into a generated field with nothing registered by hand. That was not true when this page was first built: the atoms addressed the label around the control, a label has nothing to write into, and the write was dropped without a word. Building this found it and the atoms were fixed, which is the whole argument for building a demo rather than describing one.

Ask for a message box and you get one now. Until this page was built the demo refused that request, and the refusal was honest: the design system had no rule for a textarea at all, so the only thing it could have rendered was a single-line input that swallows a paragraph. Two atoms closed that, the box you see is a real textarea in the same frame as every other control, and the desk types into it the same way it types into a name. The refusal below is what is left, and it is a shorter list than it was.

Spec

Exactly what matchSpec returned: the fields, the message box, the choices and any refusal above all come straight from this, never a second hand-typed description of it. The choices are addressable too, and the desk still leaves them alone: a select accepts a write that a text field would, and anything that is not one of its option values empties it rather than failing. So the code that drafts these demo values refuses to draft one for a choice at all. Knowing the difference is the caller's job, and that is the honest state of it rather than a solved problem.

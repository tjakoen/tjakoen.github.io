Live form

One tag renders whatever matchSpec decided, every time. It never changes between runs:

<b-field each="fields"></b-field>
<b-choice each="choices"></b-choice>

Fields are grouped by kind, text fields first and choices after. Interleaving them in the order you asked isn't supported, on purpose, a v1 limit. Labels above are the closed set's own defaults; a model could reword them (matchSpec's applyWording seam exists for exactly that), but it isn't wired into this live page, because the in-browser model runs after the page has already rendered.

So be clear about who wrote what here: nothing on this page was written by the model. The labels are the closed set's, and the demo values the desk types in are drafted by code as well, because an action the desk performs never gets a model tail. What you are watching is selection and operation, which is the part a small model cannot do, and the wording pass is still an open seam rather than a shipped one.

One more thing worth knowing before you trust the live fill: the atoms put the field's address on the wrapping label, and a label has nothing to write into, so this page moves each address down onto its own control before the desk reads it. Until that moves upstream, a generated form is addressable the moment it renders but not yet fillable without that one adjustment. The choices are left alone on purpose, and the note under the spec says why.

Spec

Exactly what matchSpec returned: the fields, the choices, and any refusal above all come straight from this, never a second hand-typed description of it. The choices keep their address on the label rather than on the select, which leaves them visible here and out of reach of the desk. A write aimed at a select does nothing useful: anything that is not one of its option values empties it instead, and it does that quietly, so the safer default is a control the desk cannot reach at all.

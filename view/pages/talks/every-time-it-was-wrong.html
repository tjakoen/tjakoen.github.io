Every Time It Was Wrong

How the PR reviewer decides what it is allowed to say.

Tjakoen Stolk

  • One line of framing: this is what I built on top of our review harness, what happened when I started grading its comments, and the things it taught me that I did not expect.
  • Questions mid-way are fine. This is a working session.
  • The rougher typeface means a machine drafted the line. Say it once and move on.

The thing itself

It reads a pull request and leaves up to six comments.

  • It posts them itself. I do not see them first.
  • It can block a merge. It cannot approve one.
  • Later, every comment it left gets marked right or wrong.
  • Three facts, no defence yet. The rest of the session is why each one is the way it is.
  • If somebody objects to the no-draft-step now, park it. There is a slide for exactly that.

Credit where it belongs

Most of this was already ours.

  • The team built the review harness and the six specialist reviewers.
  • I added the part that checks whether a comment was any good.
  • Be specific: our harness resolves the target, checks it out in isolation, runs the reviewers in parallel and assembles one verdict. The six lenses are our TypeScript reviewer set, one for one.
  • Mine: the order of evidence, the second reader, finding the right line, keeping the volume down, and the log.
  • Do not oversell the delta. The measurement is the only part worth this room's time.

One run, left to right

  • Do not walk the boxes. Point at the last panel and say the design is subtractive.
  • Volume caps are hard: six comments, three on a small change. Anything over the cap goes in the summary or gets deleted.
  • Cost, if asked: about 57k tokens of instructions load before it reads a line, six reviewers run in parallel, and the arguing-against step is the most expensive thing it does.

A comment has to pass all five, or it is dropped

  • Move fast. Only the third one is interesting and the next two slides are about it.
  • Worth one line: a comment that fails a rule is dropped, or turned into a question. It is never softened and posted anyway.

Rule three, and how it fooled me

It searched the file it was reviewing.

  • Found the pattern. Quoted it. Said the code was fine.
  • Of course the file matches itself. That is what made the check feel like proof.
  • Give them a beat before the second line. Most people get there on their own.
  • The fix: count across the whole service, and put the count in the comment. "We do it this way here" and "we do it that way 546 times and this way twice" are different claims, and only the second one survives someone disagreeing.
  • The case behind the rule: 872 of the right pattern against 2 of the wrong one across the service, and the wrong one sat 18 lines away in the same file, which is why it passed. A human asked for changes on that line the next morning.
  • Second failure: where the code has drifted, the neighbours are the drift, so a reviewer that only searches will defend the exact pattern our reviewers keep rejecting.

So the code around the change is the weakest evidence, not the strongest

  • Read it bottom to top: that is the order of temptation, because searching the code is the easiest thing to do and it is the bottom rung.
  • The top rung is fed only by comments we measured as wrong, and nothing else can add to it. It has five entries.
  • The right-hand panel exists because we lost a real accessibility finding to a neighbouring file before it did.

What survives gets sorted into two piles

  • This split came out of our own plugin work and it was the best idea I took. Asking a model to second-guess a fact only risks it talking you out of something true.
  • Third case if asked: the pattern is certain but the impact is not. Treated as an opinion.

Every opinion goes to a second reader

Whose whole job is to prove it wrong.

  • It gets the claim on its own, with the reasoning removed, so it cannot just agree.
  • If it cannot decide, the answer is no.
  • A comment that loses is deleted, not reworded more gently.
  • Removing the reasoning matters. Show a verifier the original argument and it tends to agree with it.
  • What it is asked: can this code path actually be reached, is it already handled further down the file, does the quoted example really support the claim, and did the ticket ask for it.
  • We cap how many claims one reader gets, on wall-clock rather than cost, because a reader holding a dozen of them stops arguing and starts summarizing.

Then one last question per comment

What actually breaks?

  • "This looks wrong" does not count.
  • "Delete this and every caller reads the wrong customer's data" does.
  • Anything in between becomes a question, or nothing.
  • This rule is what replaced me reading every review before it went out. Say that plainly.
  • The tie-break never moves: a wrong comment sticks around and a missed one costs you one PR, so when it is close, say nothing.

The one nobody warns you about

The pull request carries on while the run is thinking.

  • A run takes minutes, and people keep working through those minutes.
  • So the last step before posting is reading the PR again and dropping whatever got answered.
  • Real case: a person asked for changes about thirty seconds before this thing posted a clean verdict on the same commit. Two opposite reviews, a minute apart.
  • The subtle part: compare against when you last read the comments, not when the run started. Two different times, and only one of them catches this.
  • Also worth knowing: a review submitted with no line comments shows up on one API endpoint and not the other, which is how we missed that one.

Two halves of the same decision

It posts on its own. It gets no vote.

  • A review I have to read before it goes out is one I would never find time to run.
  • Merging needs human approvals, and an approval from this account would count as one.
  • So it can hold a merge. Only I can let one through.
  • Expect the pushback here. The answer is the re-read before posting, not confidence.
  • This is a control, not a preference. No accuracy number would change it.
  • Consequence worth flagging: blocking does not clear itself when the author pushes a fix, so it is only spent where we mean to hold the PR until a person acts.

Then we graded them, and this was the surprise

  • Top half first: both groups were right. This is not an accuracy problem.
  • 405 of the logged comments sit in the summary against 285 on a line, so most of what it says lands in the part nobody reads.
  • Clearest single case: a confirmed bug tucked into a collapsed summary block was the one thing an author missed while fixing all four of the line comments.

Which I had as one number for months

  • The consequence is the point: every time it got ignored, my own numbers told me to make it stricter. It was learning to say less for being read less.
  • They need opposite fixes. Being wrong means tighten the reviewer. Being ignored means move the comment somewhere people read, and tightening there just throws away true findings.
  • Say it once as a general rule: any measure that mixes "was I right" with "did anyone listen" will tell you to shut up.
  • Honest caveat: three changes aimed at that number inside eight days, so I cannot say which one worked. I broke my own measurement.

Posting is not the end. Somebody answers

  • Where it started: a timer every thirty minutes. Forty-eight wake-ups a day, each one a fresh session holding a single line of output, filed nowhere.
  • Being told is far better for the normal case, because the message arrives at the session that already has the whole review in its head. Answering a reply costs a fraction of starting over.
  • The silent close is why the timer survives. Nothing moves, so nothing can tell us, and around here going quiet is how people agree. Five out of five silently closed threads turned out to be real fixes.
  • The timer half is a shell script, one call per PR, and it prints nothing when nothing changed. A check that talks every time is a check nobody reads.

And a warning about all of this

My own docs described that timer in detail. It had never existed.

  • Nothing pointed at it. The folder was never created. It had not run once.
  • It lasted weeks because it sounded right and nobody ran the command.
  • Second time this exact shape has caught me. Mention there is a whole post about the first one, do not retell it.
  • The lesson for anyone building this kind of thing: write down what a system does and you will start believing your own writing. Go and measure instead.

What the grading is actually for

  • Grading from the code matters: most items get no reply at all, so going by replies alone measures the quarter you were surest about.
  • The try-it-on-old-PRs step is the one people skip. Report what it caught, how often it was right and how much it said, all three: catching more while saying twice as much is not an improvement.
  • Grading only what got posted is blind to what it missed, so there is a separate pass that reads human comments on files the reviewer looked at and said nothing about.

The one rule I will not move

Let it tune itself on its own output and it will only ever learn to say less.

  • Concretely: it cannot raise its own bar, cannot give itself more comments, and cannot add to the list that silences a whole class of finding. Each of those stops and asks.
  • "It can tell me it was wrong. It does not get to decide what to do about that."

If you are building something like this

  • This is the slide worth the room's time. Offer it as the real takeaway: none of it was designed up front, and it could not have been.
  • If there is time, the volume caps are the sharpest one: written once on an authority nobody had given, and reverted for it.
  • Open the floor here rather than at the end.

Every Time It Was Wrong

How the PR reviewer decides what it has earned the right to say.

Tjakoen Stolk

  • Frame it in one line: this is what I built on top of our review harness, what it measured, and the three things it taught me that I did not expect.
  • Say up front that questions mid-way are fine. This is a working session, not a keynote.
  • The rougher typeface means a machine drafted the line. Mention once, do not come back to it.

The thing itself

Reads a PR, posts up to six line comments.

  • No draft step. It posts.
  • It can block a merge. It cannot approve one.
  • Every comment it posts gets graded later.
  • Three facts, no defence yet. The rest of the session is why each one is the way it is.
  • If somebody objects to the no-draft-step now, park it: slide 12 is exactly that.

Credit where it belongs

Most of the machine is ours already.

  • The harness, the worktree, the six lenses, the checklists: all team-built.
  • I added the part that asks whether a finding was right.
  • Be specific about the inheritance: target resolution, isolated checkout, parallel dispatch, one assembled verdict. The lens set is the TypeScript reviewer set, one for one.
  • What is mine: the precedence ladder, the verification pass, anchors resolved from excerpts, the volume discipline, and the outcome log.
  • Do not oversell the delta. The interesting half is the measurement and that is the only part worth this room's time.

One run

  • Do not walk the boxes. Point at the narrowing and say the design is subtractive: everything below the lenses exists to remove findings.
  • Volume caps are hard. Six inline, three on a small or incremental diff. Anything over the cap folds into the body or gets deleted.
  • Costs, if asked: roughly 57k tokens of instruction load before it reads a diff, six lens agents in parallel, then a verification pass that is the single most expensive step.

Every finding clears all five, or it is dropped

  • Intent. Traced to the ticket and the epic. A change that was asked for is not a finding.
  • Prior art. Not already raised, not already answered.
  • Cross-pattern. The convention is grepped and cited, never asserted.
  • Line accuracy. The anchor is resolved from the excerpt, not read off a hunk header.
  • Necessity. Worth the author's time.
  • Move fast here. Only the third one is interesting and the next two slides are about it.
  • Worth one line: a finding that fails a gate is dropped or downgraded to a question. Never softened and posted anyway.

Gate three, and where it went wrong

It grepped the file it was reviewing.

  • Found the pattern. Cited it. Approved the code.
  • A file contains the pattern it is about to bless, by construction.
  • Give them two seconds before the second beat. Most people get there.
  • The fix: count across the owning service, and put the count in the finding. "The idiom here is X" and "X appears 546 times against this shape's 2" are different claims and only the second survives disagreement.
  • The case that produced the rule: 872 permission checks against 2 role-gate call sites service-wide, and the wrong one sat 18 lines away in the same file, which is why it passed. A human requested changes on that line the next morning.
  • Second failure worth naming: where the code has drifted, the neighbours certify the drift, so a reviewer that only greps will defend the pattern our own reviewers keep rejecting.

So the surrounding code is the weakest evidence, not the strongest

  • Read it bottom to top: that is the order of temptation, because grepping is the easiest thing to do and it is the bottom rung.
  • The top rung is fed only by findings measured wrong, and nothing else can write to it. That is the highest-precedence rule in the whole skill and it has five entries.
  • The right-hand panel is the carve-out that cost us a real accessibility finding before it existed. Let them read it rather than reading it out.

Everything that survives gets sorted

  • Fact about the diff. No spec file for this changed service. A script proves it every time. Straight through.
  • Claim about the world. This is an authorization hole. That is reasoning. Always verified.
  • This split came from our own plugin work and it was the best idea I took. Handing a fact to a model only risks it talking you out of something true.
  • Third case if asked: the pattern is certain but the impact is not. Verified like a claim.

Every claim goes to a second reader

Whose only job is to refute it.

  • Handed the claim with the reasoning stripped out.
  • Uncertain defaults to refuted.
  • Refuted means dropped. Not softened.
  • Stripping the evidence matters: a verifier shown the original argument tends to agree with it.
  • What it is asked: is the failure reachable, is it already handled in the same file, does the cited sibling actually support the claim, is it the ticket's intent.
  • Batching: capped on wall clock rather than tokens, because one reader holding a dozen claims stops attacking and starts summarizing.

Then one question per finding

Name what breaks.

  • "This looks wrong" is not a finding.
  • "Delete this and every caller reads the wrong tenant" is.
  • Short of that: downgraded to a question, or cut.
  • This is the rule that replaced me reading each review before it went out. Say that plainly.
  • The tie-break, and it never moves: a wrong comment is permanent and a missed one is one PR, so when the two are close, drop it.

The one nobody warns you about

The PR is alive while the run is thinking.

  • A run takes minutes. Reviewers and authors act inside those minutes.
  • So the last step before posting is reading the PR again and dropping anything that got answered.
  • Real case: a human requested changes about thirty seconds before this thing posted a clean verdict on the same commit. Two contradictory reviews, one minute apart.
  • The subtle bug: compare against when you last read the threads, not when the run started. Different timestamps, and only one of them catches this.
  • Also worth knowing: a review submitted with no inline comments exists only on the reviews endpoint and is invisible on the comments listing. That is how the above went unseen.

The two halves of one decision

It publishes on its own. It holds no vote.

  • A review I have to read before it posts is one I would not have time to run.
  • Merging needs human approving reviews, and the posting account would satisfy that gate.
  • So it can block a merge. Only I can release one.
  • Expect the pushback here. The answer is the pre-post gate, not confidence.
  • This is a control, not a preference. No precision number would change it.
  • Consequence worth flagging: a change request does not clear itself on a fix push, so blocking is spent only where you mean to hold the PR until a person acts.

Then we measured it, and this was the surprise

  • Top half first: both groups were right. This is not an accuracy story.
  • 405 of the logged findings sit in the body against 285 inline, so the majority of what it says lands in the region nobody reads.
  • Direct evidence that the fold is the cause: on one PR a confirmed bug folded into a details block was the one item the author missed while fixing all four inline comments.

Which I had as one number for months

  • Precision. Was it right? Fixed over fixed plus proven wrong.
  • Adoption. Did anyone act? Fixed over fixed plus ignored.
  • Fused, an author merging past a correct comment scores as the reviewer being wrong.
  • The consequence is the point: every time it got ignored, my own dashboard told me to make it stricter. It was learning to say less for being read less.
  • They want opposite repairs. Low precision is a lens to tighten. Low adoption is a placement problem, and tightening the lens there throws away true findings.
  • Generalize it once: any metric that fuses "was I right" with "did anyone listen" will tell you to shut up.
  • Honest caveat: three changes aimed at that number inside eight days, so I cannot yet say which one worked. That is a measurement I broke.

Posting is not the end. Somebody replies

  • Where it started: a timer every thirty minutes. Forty-eight wake-ups a day, each a fresh session holding one line of output, filed nowhere.
  • The event half is strictly better for the common case, because the wake arrives at the session that already holds the review in context. Answering a reply costs a fraction of re-running anything.
  • The silent resolve is why the poll survives. Nothing moves, so nothing can notify, and around here silence is how people agree. Five of five silently-resolved threads turned out to be real fixes.
  • The poll is shell, one call per PR, and prints nothing when nothing changed. A poll that talks every tick is a poll nobody reads.

And a caution about all of this

My own docs described that poller in detail. It had never existed.

  • Nothing referenced it. The directory was never created.
  • It survived weeks because it was plausible and nobody ran the command.
  • Second time I have been caught by exactly this shape. Mention that there is a whole post about the first one, do not retell it.
  • The lesson is the one that matters most for anyone building this kind of thing: write down what a system does and you will start believing the writing. Measure instead of reading.

What the log is actually for

  • The scoring-from-code half matters: most items have no thread, so reading thread state alone measures the quarter of the output you were most confident about.
  • The re-run step is the one people skip. Report recall, precision and volume together: a change that raises what you catch while doubling what you say is not an improvement.
  • Precision scoring is blind to a miss by construction, so there is a separate recall pass that reads human comments on files the reviewer looked at and never flagged.

The rule that keeps the loop honest

A loop allowed to tighten itself on its own output can only ever learn to say less.

  • Concretely: it cannot raise its own severity bar, cannot widen its own volume caps, and cannot add to the list that silences a class of finding. Those stop and ask, every time.
  • "It can tell me it is wrong. It does not get to decide what to do about being wrong."

For anyone building something similar

  • Polling on a timer, before events.
  • One verifier per finding, before somebody priced a twelve-finding review.
  • The whole standards file loaded into every lens, seven times a run.
  • Precision and adoption as one number.
  • Logging only the inline comments, which measured the quarter it was surest about.
  • An increment range that would have reviewed two thousand files of somebody else's work.
  • Every one of those needed shipping the wrong version and then measuring it.
  • This is the slide worth the room's time. Offer it as the actual takeaway: none of this was designed up front and it could not have been.
  • If there is time, the volume sub-caps are the sharpest one: written once on an authority nobody had granted, and reverted for it.
  • Open the floor here rather than at the end.

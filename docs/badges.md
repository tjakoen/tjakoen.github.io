# Course badges

An award recognizes a designated badging activity at its published threshold, after the instructor reviews the work and approves the award. Participation in a term is insufficient. The private course platform owns eligibility, identity reconciliation, the roster, and delivery. The portfolio publishes approved credentials.

The issuer reads a private version 1 manifest. Each award contains an explicit approval, a stable award key, the badge identifier and criteria, verified recipient name and GitHub account, one verified identity email, and reviewed evidence. The email is used only for a salted recipient hash. Private recipient keys, workspace repositories, student numbers, and raw recipient emails are not written into portfolio output. Recipient names appear only on their individual certificates, not on class pages or the hub.

```sh
bun tools/issue-badges.ts --manifest /private/approved-awards.json
bun tools/issue-badges.ts --manifest /private/approved-awards.json --emit --issued-manifest /private/issued-awards.json
bun tools/badge-images.ts
```

The first command validates every award and prints counts without writing. The emission command also writes a private issued manifest with the original award fields and the final certificate identifiers, Manila issue date, share URL, and image URL. The course platform uses that record for roster updates and delivery. The issued manifest is written only during emission. An explicit --preview-manifest path produces a private projection during a dry run, marked as a preview; it must not be used as evidence of publication. Emission is a separate operation. The manifest must live outside this public repository. Approval of implementation does not approve a batch of student awards.

The manifest has schemaVersion 1 and an awards array. Each award includes thresholdPercent 75 and a nonempty activities array. Each activity has id, title, and a generic public description of the work completed. The combined APSI midterm award lists both designated activities on the same certificate; its criteria require a reviewed score of at least 75% on M5A4 Relational REST API and on M5A5 React client independently. An average cannot compensate for an activity below the threshold. Award fields are awardKey, approved, badgeId, course, monogram, section, term, title, description, criteria, recipientKey, recipientName, recipientHandle, identityEmail, workspaceRepo, and evidence. Evidence is an array of HTTPS URLs with optional full commit hashes, retained only in the private manifest. Per-activity evidence has the same private role. Optional publicEvidence at award or activity level contains links explicitly checked and approved for publication; those links must point to public GitHub work outside the course organizations and private student workspaces. The issuer does not turn private audit evidence into public links. The optional issuedOn, certSlug, certId, and shortId fields support an explicitly reconciled existing award. The course platform must supply evidence safe for public publication. Never supply private workspace links or student identifiers as evidence.

New certificate slugs and short links derive from an opaque hash of the award key. Repeated issuance preserves dates, identifiers, and recipient hash salts. Existing awards are matched through a hashed award key or an explicit certificate slug. Conflicting identity data stops the whole batch. A certificate URL can be reconciled only to the same badge class, and an approved certificate cannot be reused for a different award key. Original certificate files and short links remain available. Incremental batches retain existing class links on the hub and count previously approved recipients alongside the new recipients. Legacy classes remain labeled as legacy.

Existing certificates absent from the manifest hold emission. The instructor may explicitly choose --allow-existing to preserve those legacy awards while issuing the reviewed batch. That flag does not validate their eligibility, revoke them, remove them, or upgrade their assertions. Reconcile those records separately before treating the old batch as reviewed.

New assertions use [Open Badges 2 hosted verification](https://www.imsglobal.org/spec/ob/v2p0/), with an embedded BadgeClass and issuer Profile, an email hash with a random stable salt, evidence, and the downloadable PNG URL. The JSON remains available through the existing certificate .json route, backed by its .ob.json file. Hosting provides verification through the issuer's site. These are not signed Open Badges 3 credentials, and interoperability with a particular badge importer still needs an actual import test.

The manifest can describe prelim, finals, and multiple midterm achievements independently. The instructor confirmed one combined APSI midterm badge requiring both badging activities. Each activity must meet its threshold independently. The portfolio does not infer activities from module ranges or manufacture scores.

After publishing and verifying the certificate and PNG links, the course platform records those links in its private roster and delivers them in each student's workspace. Email delivery to verified school and personal addresses uses the same approved award record and an idempotent delivery ledger. A draft email or failed delivery is not evidence that an award reached the student.

Historical participation certificates display a reconciliation notice and label their JSON as legacy award metadata. The page does not present the current achievement criteria as something those legacy recipients have met. Their existing files and images remain unchanged until the instructor decides how to reconcile them.

Certificates describe the activities completed and show the 75% award threshold. Class pages describe the same activities without recipient-specific evidence. Legacy participation pages retain their historical distinction and do not acquire these current achievement claims.

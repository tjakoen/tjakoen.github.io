# The third time you type it, save it

Status: DRAFT script for Tjakoen to read aloud and edit. Not yet read or checked by him.

Same format as the other scripts: one idea a beat, about 20 to 45 seconds, names the phrase in the note that lights up, and adds the why or the practice instead of repeating the page. Skills and routines were covered in Claude Academy, so define them in a clause and tell the listener to ask their agent.

## Stop 1: A prompt you've earned

**Beat 1**
highlight: intro | That tiredness is useful.

You've typed the same prompts a few times now. The plan one, the check one, and adding a roadmap entry. You're a bit tired of them. That tiredness is useful, because it's telling you what to save.

**Beat 2**
highlight: a-skill-is-a-prompt-youve-earned | Don't write a skill until you've typed the thing three times by hand.

A skill is a saved set of instructions your agent can run when you ask. Academy covers how. What I give you is the rule for when. Don't write one until you've typed it three times by hand. Before that, you're guessing what it should say.

**Beat 3**
highlight: a-skill-is-a-prompt-youve-earned | Every correction you give twice

And every correction you give twice is a line waiting to go in. That's how it ends up sounding like how you work, and not like a template.

**Digest:** A skill is a saved prompt. Wait until you've typed it three times by hand, then you know what it should say. Every correction you give twice is a line to add.

**Trial:** Name the prompts you've typed most in the last few notes.

**Runes:**
three-times | Don't write a skill until you've typed the thing three times by hand.

## Stop 2: Let your agent write it

**Beat 1**
highlight: let-your-agent-write-it-then-you-edit-it | Turn what we just did into a skill.

Don't start from a blank page. Right after a session where the prompt worked, say: turn what we just did into a skill. Then read it the way you'd read a plan. When does it say to use it? Are those the steps you'd take? Is something in there you never asked for?

**Beat 2**
highlight: let-your-agent-write-it-then-you-edit-it | Keep a skill to one job.

A good one for your portfolio is adding a roadmap entry. It asks what you learned, in your own words, adds the entry with a date and a link, and checks the link opens. It doesn't write your words for you. Keep a skill to one job, and save it in the project next to your brief and plan, so every session finds it. Then as you catch new misses, add a line. That's how it gets better. Later in the path you'll meet my loop, which notices when I repeat a request and asks if I want a skill. For now, you're the one noticing.

**Beat 3**
highlight: keep-judgment-manual | an audit is a judgment

One more thing. Not every skill should run by itself. I run my audits by hand. My loop tells me when one is due and I decide to go. That's a preference, but the reason is that an audit is a judgment, and I want to be in the room for it.

**Digest:** Ask your agent to turn a session that worked into a skill, then edit it. One job per skill, saved in the project. Later you'll meet a loop that notices repeats for you, but by hand comes first. Keep judgment work, like audits, manual.

**Trial:** Pick the prompt you've typed most, or the roadmap entry one, ask your agent to turn it into a skill, edit it, save it in your project, and use it to add your next entry.

**Runes:**
one-job | Keep a skill to one job.

## Stop 3: When a skill earns a routine

**Beat 1**
highlight: when-a-skill-earns-a-routine | It has to be repeated, boring, and

A routine, sometimes called a scheduled loop, runs a skill on a timer or when something happens, with you nowhere in sight. Your agent can show you how yours does it. Same test as for a skill, plus one clause. It has to be repeated, boring, and checkable, so you can tell it worked without reading its mind.

**Beat 2**
highlight: when-a-skill-earns-a-routine | moves tickets that are due for code review

Mine are plain. One checks whether my classes are graded. One moves tickets that are due for code review into the reviewer's queue. One updates my team's metrics calculations. Nobody makes a judgment call in any of them, and a wrong result is easy to spot.

**Beat 3**
highlight: when-a-skill-earns-a-routine | No audits.

Look at what's missing. No audits. Nothing that edits code and ships it unreviewed. A routine that does something you'd have to think about doesn't save time. It files a mess for you to sort out later.

**Beat 4**
highlight: when-a-skill-earns-a-routine | needs something that tells you when it didn't

And check it actually ran. I once trusted a check for three weeks before counting and finding it had run once in a hundred and sixty-five sessions. Anything that runs while you're not looking needs something that tells you when it didn't.

**Beat 5**
highlight: try-this | Don't build the routine yet.

Your trial. Skill first. Then write down one chore that's boring and checkable, and don't build the routine yet. Just notice it's there. Your skills will look nothing like mine, and that's the point.

**Digest:** A routine runs a skill on a schedule. Build one only for work that is repeated, boring and checkable. Never schedule judgment, and make something tell you when a routine did not run.

**Trial:** Write down one chore that is boring and checkable, such as checking that the links on your roadmap still open. Do not build the routine yet.

**Runes:**
routine-test | It has to be repeated, boring, and
routine-ran | needs something that tells you when it didn't
